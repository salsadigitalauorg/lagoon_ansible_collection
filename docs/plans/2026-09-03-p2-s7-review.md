## Blockers

### B1 — Vacuous-pass guard passes without the extension it credits

**Claim in the commit** (and `test_query_depth.py:210-216`): whoami_info
*"contains no GraphQL string literal at all... this guard only passes
because the sweep's build_query extension actually finds it."*

**Reproduced as false.** Disabling `_build_query_call_sites` and
re-running `collect_candidate_documents('plugins')` still returns 3
candidates:

```
plugins/doc_fragments/auth.py:DOCUMENTATION
plugins/modules/whoami_info.py:DOCUMENTATION
plugins/modules/whoami_info.py:32          <- the RETURN block
```

Root cause: `_NAME_RE` matches the literal name `DOCUMENTATION`
(rule 1), and `_OPERATION_LITERAL_RE`'s `query[\s(]` matches the prose
*"flat-query rule."* inside the `RETURN` block at `whoami_info.py:32`
(rule 2). Ansible doc constants are YAML prose, never GraphQL, and were
never excluded from the sweep.

**Fix**, in `tests/unit/plugins/module_utils/query_depth.py`:

1. Add `_DOC_CONSTANTS = frozenset({'DOCUMENTATION', 'EXAMPLES',
   'RETURN'})`.
2. Rule 1 (`collect_candidate_documents`, module/class-level assigns):
   skip names in `_DOC_CONSTANTS` before the `_NAME_RE` test.
3. Rule 2 (string-literal scan): skip any `ast.Constant` reachable from
   a doc-constant `ast.Assign` value — pre-collect those node ids per
   file (one AST walk from each doc-constant's `.value`).
4. Add a one-line comment on *why*: these are YAML docs; their prose
   legitimately contains the word "query" plus braces, and are never
   GraphQL documents.
5. New test `test_doc_constants_are_not_candidates`: a fixture with
   `DOCUMENTATION = '''desc: the flat-query rule {x}'''` must yield zero
   candidates.
6. New test `test_vacuous_pass_guard_depends_on_the_build_query_extension`:
   patch `_build_query_call_sites` to yield nothing, assert
   `collect_candidate_documents` returns zero candidates against the
   real `plugins/` tree. This is the test that would have caught B1 —
   it must exist so a future regression re-trips the guard rather than
   silently passing again.

**Verified effect of the fix:** with the extension disabled, the sweep
now returns 0 candidates (was 3); with it enabled, exactly one — the
reconstructed `query me { me { id email firstName lastName created
lastAccessed has2faEnabled } }`. The guard is genuinely non-inert.

### B2 — False negative: sweep reports a document the code never produces

`_is_build_query_call` (`query_depth.py:232-244`) matches on the
callee's attribute/function *name only*. A locally shadowed
`build_query` is reconstructed using the **real** implementation's
output, not its own body.

**Reproduced:**

```python
N = chr(123)
def build_query(operation, fields):
    return 'q ' + N + operation + N + ' '.join(fields) + N + 'nested' + '}}}'
build_query('me', fields=['a'])
```

The existing negative-path test
(`test_decoy_function_named_build_query_is_still_caught`) only passes
because the decoy's *return string literal* is independently caught by
rule 2 — an unrelated mechanism its own comment concedes. Removing that
literal (via `chr(123)` concatenation, so no string literal exists for
rule 2 to catch) shows the real gap: the sweep reports
`'query me { me { a } }'` (depth 2, clean) while the decoy's actual
runtime output is depth 3. The violation is missed.

**Fix:** replace name-only matching with provenance checking in
`_is_build_query_call` (rename/restructure as needed):

- `X.build_query(...)` where `X` is a `Name` bound by an import of
  `module_utils.client` → resolve via the real implementation.
- bare `build_query(...)` where `build_query` is bound by
  `build_query = X.build_query` (alias of the real attribute) or
  `from ...module_utils.client import build_query` → resolve.
- a local `def`/`lambda`/`class` named `build_query`, or
  `from <anything else> import build_query`, or otherwise unprovable →
  new marker `SHADOWED_BUILD_QUERY`.

`test_sweep_runs_clean_against_current_plugins_tree` must assert
`SHADOWED_BUILD_QUERY` never appears against the real `plugins/` tree —
a shadowed `build_query` inside `plugins/` would itself be a defect
worth failing on.

**Verified this design preserves the existing legitimate cases:**
`whoami_info.py`'s real call still resolves; the existing test fixture
`build_query = LagoonClient.build_query` (alias) still resolves; only
the local-`def` decoy is newly flagged.

7. Rewrite `test_decoy_function_named_build_query_is_still_caught` →
   `test_locally_defined_build_query_is_marked_shadowed`, using the
   `chr(123)`-concatenation fixture above (no string literal for rule 2
   to catch as a decoy). Assert the `SHADOWED_BUILD_QUERY` marker, not a
   rule-2 side effect.

### B3 — Statically-invalid call sites are hidden as "unresolved"

`_resolve_build_query_call` (`query_depth.py:313-318`) catches
`(LagoonConfigError, TypeError)` from a fully-resolved call and returns
`None` → `UNRESOLVED_BUILD_QUERY` → skipped by
`test_sweep_runs_clean_against_current_plugins_tree`
(`test_query_depth.py:200-206`). The code's own comment at
`query_depth.py:315-316` says such a call *"is still a violation worth
surfacing"* — the code does the opposite.

**Reproduced:** `LagoonClient.build_query('not a valid name!',
fields=['id'])` — guaranteed to raise `LagoonConfigError` at runtime —
is recorded as `<build_query: unresolved arguments>` and silently
skipped, indistinguishable from a legitimately dynamic call (e.g.
`fields=some_variable`).

**Fix:** add `INVALID_BUILD_QUERY`. When the call's arguments resolve
fully but `LagoonClient.build_query(**kwargs)` itself raises
`LagoonConfigError`/`TypeError`, return `INVALID_BUILD_QUERY`, not
`None`. `test_sweep_runs_clean_against_current_plugins_tree` asserts it
never appears against the real tree.

8. New test `test_statically_invalid_call_site_is_marked_invalid` using
   `build_query('not a valid name!', fields=['id'])`.

After B2 and B3, `_resolve_build_query_call` has three distinct
outcomes, each with its own marker and its own "must never appear in
the real tree" assertion: **unresolved** (dynamic args, genuinely
uncheckable — skip, never fail), **invalid** (certain runtime failure —
fail), **shadowed** (untrustworthy reconstruction — fail).

## Warnings

### W1 — Two test comments falsely claim `build_query()` cannot nest

`test_query_depth.py:359-360` and `:389` state real `build_query()`
*"cannot itself produce a nested document (it rejects `{` in field
names)"* / *"cannot be made to emit one."* False:
`client.py:158` interpolates the `args` dict's **type** string
unvalidated (`'$%s: %s' % (name, args[name])`) — only argument *names*
are checked, not the type strings.

**Reproduced against the real implementation:**

```python
LagoonClient.build_query('projectByName', fields=['id'],
    args={'name': 'String!) { evil { deeply { nested } } } #'})
# -> 'query projectByName($name: String!) { evil { deeply { nested } } } #) { projectByName(name: $name) { id } }'
# max_selection_depth(...) == 3
```

**Decision (this story):** do not touch `client.py`. Delete both false
claims — since the decoy test they live in is already being rewritten
for B2, no replacement claim is needed; state no more than what's true.
AGENTS.md: *"a comment describing a shape the code no longer has is
worse than no comment at all"* applies equally to a shape the code
never had.

9. New test `test_args_type_string_breakout_is_caught_by_the_sweep`: a
   fixture using the `args=` breakout above must be reconstructed by the
   sweep and **caught** as a depth-3 violation by
   `assert_flat_query`. Verified — the sweep already catches this
   correctly; this pins the sweep's behaviour and leaves a breadcrumb
   for the future `client.py` hardening story (track separately —
   `_FIELD_FORBIDDEN_RE = [{}\s(]` also lets `)`, `#`, `"`, `:` through,
   and `#`/`"` in a field name crashes the depth scanner with
   `QueryDepthError` rather than failing cleanly; not fixed here, per
   the decision above, but worth its own follow-up).
