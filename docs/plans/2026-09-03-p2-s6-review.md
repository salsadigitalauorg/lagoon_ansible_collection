## Blocker

### B1 — The shim silently drops the `BatchMode=yes` SSH default

`plugins/action/__init__.py:121-124` sets every boolean config key
unconditionally, using `None` as the "absent" marker:

```python
for arg_key, config_key in _BOOL_KEYS:
    value = self._resolve_value(arg_key, task_vars)
    config[config_key] = _to_bool(value) if value is not None \
        else None
```

But `resolve_token` reads `batch_mode` with a **two-argument `.get()`**, not an
`or`-style fallback — `plugins/module_utils/auth.py:224`:

```python
batch_mode=config.get('batch_mode', True),
```

`.get(k, default)` only returns the default when the key is **absent**. The
shim always *inserts* the key, so the value passed is `None`, and
`ssh.py`'s `_build_argv` treats that as falsy and emits nothing:

```python
# plugins/module_utils/ssh.py:176-177
if batch_mode:
    argv += ['-o', 'BatchMode=yes']
```

**Reproduced.** A shim-driven grant versus the identical no-shim
`resolve_token({'ssh_host': ...})` call, both with `subprocess.run` mocked:

```
SHIM PATH:     ['ssh', '-p', '22', '-o', 'StrictHostKeyChecking=accept-new',
                '-o', 'ConnectTimeout=30', 'lagoon@h.example', 'grant']
NO-SHIM PATH:  [... 'ConnectTimeout=30', '-o', 'BatchMode=yes', ...]
```

`BatchMode=yes` is present without the shim and absent with it.

**Why this is a Blocker, not a Warning.** P2-S3b landed this default
specifically as the backstop for a failure mode nothing else covers, and
`ssh.py:64-74` documents it:

> `batch_mode` defaults to `True`, emitting `-o BatchMode=yes` so a grant
> that cannot authenticate (e.g. an agent holding no usable key) fails
> immediately instead of falling through to an interactive
> passphrase/host-key prompt that Ansible has no way to answer.
> `ConnectTimeout`/`timeout` do not cover this case […] so without
> `BatchMode` the only backstop is `subprocess.run(timeout=...)` itself,
> which turns a prompt into an opaque multi-second stall rather than a clean
> auth failure.

This meets the **demonstrable failure** bar: the trigger sequence is any
agent-auth grant through the shim (the path P2-D9 made reachable and that
AWX/ansible-runner relies on) where the agent holds no usable key. The
documented "fail fast" behaviour becomes a 30-second stall ending in an
opaque timeout. It is also a **cross-story regression** — P2-S3b's
`TestBatchMode` still passes because it tests `request_grant` directly,
never through the shim, so the suite is green while the shipped default is
defeated.

**Remediation.** Omit absent keys instead of inserting `None`, so
`resolve_token`'s own defaults apply. Minimal fix:

```python
for arg_key, config_key in _BOOL_KEYS:
    value = self._resolve_value(arg_key, task_vars)
    if value is not None:
        config[config_key] = _to_bool(value)
```

Apply the same "only set if resolved" shape to `_INT_KEYS`, `_STR_KEYS` and
`validate_certs` — it is the correct contract for a dict consumed via
`.get()` throughout, and it removes a whole class of this bug rather than
patching one instance.

**Add a regression test that goes through the shim**, asserting argv
contains `BatchMode=yes`, not just that `config['batch_mode']` is truthy.
The existing `TestBoolAndIntCoercion` asserts on the config dict, which is
exactly why this slipped through. A shim→`resolve_token`→`request_grant`
argv assertion is the test that would have caught it.

## Warnings

### W1 — `_build_auth_config` sits outside the `try`, so a bare `ValueError` escapes untyped

`plugins/action/__init__.py:81-85`:

```python
config = self._build_auth_config(task_vars)
try:
    token = auth.resolve_token(config, warn=self._display.warning)
except LagoonError as e:
    raise AnsibleError(str(e))
```

The story's own illustrative design puts **both** calls inside the `try`:

```python
try:
    config = self._build_auth_config(task_vars)
    token = auth.resolve_token(config)
except LagoonError as e:
```

`_build_auth_config` can raise: `_to_int` (`__init__.py:44-49`) ends in a
bare `int(str(value).strip())` with no guard. Confirmed by test — a
`task_vars` value of `lagoon_ssh_port: 'twenty-two'` raises `ValueError`,
which is **not** an `AnsibleError`, and `resolve_token` is never reached:

```
test_garbage_port_raises_bare_valueerror_not_ansibleerror  PASSED
  assertNotIsInstance(ctx.exception, AnsibleError)  -> holds
  mock_resolve.assert_not_called()                  -> holds
```

The operator sees a Python traceback rather than a task failure naming the
bad option. AC "Auth failure never reaches `_execute_module`" is *technically*
satisfied (nothing leaks through), so this is a Warning, not a Blocker — but
it violates the collection's error-taxonomy boundary, where the shim is meant
to be the seam that converts every failure into `AnsibleError`.

**Remediation.** Have `_to_int` raise `LagoonConfigError` (naming the option,
not echoing a secret), and move `_build_auth_config` inside the `try`. That
also makes the message actionable: *"lagoon_ssh_port must be an integer"*.

### W2 — `_to_bool`'s docstring claims parity with Ansible's argspec; it does not have it

`plugins/action/__init__.py:33-36`:

```python
def _to_bool(value):
    """Coerce a possibly-templated-string boolean the way Ansible's own
    argspec does, so a ``vars:``-supplied ``"false"`` does not silently
    evaluate truthy via bare Python ``bool()``."""
```

Compared against `ansible.module_utils.parsing.convert_bool`:

| | truthy values |
| --- | --- |
| Ansible `BOOLEANS_TRUE` | `1, on, t, true, y, yes` |
| `_TRUTHY_STRINGS` (`__init__.py:10`) | `1, on, true, yes` |

`'y'` and `'t'` are true to Ansible and **false** to the shim. Worse, Ansible's
`boolean()` *raises* `TypeError` on unrecognised input, whereas `_to_bool`
returns `False` — so `lagoon_token_cache: 'tru'` (a typo) silently disables
the cache instead of erroring.

The behaviour is defensible; the docstring's parity claim is not, and
AGENTS.md requires comments to describe the code as it actually is.

**Remediation.** Either use `ansible.module_utils.parsing.convert_bool.boolean`
(available, no new dependency, and `plugins/action/` is already permitted to
import from `ansible.*`) — preferred, since it gets typo-rejection for free —
or keep the local helper and correct the docstring to state the narrower set
and the swallow-on-garbage behaviour.

### W3 — The coercion layer's justification is broader than the real gap

The plan doc justifies `_to_bool`/`_to_int` with "`task_vars` values may arrive
as templated strings". Verified in the container, that is only partly true:

```
Templar.template('{{ p }}')  with p=2222   -> 2222    int    (native type kept)
Templar.template('{{ b }}')  with b=False  -> False   bool   (native type kept)
Templar.template('2222')                   -> '2222'  str
yaml.safe_load('a: false')                 -> False   bool
yaml.safe_load("b: 'false'")               -> 'false' str
```

Ansible's Templar preserves native types through `{{ }}`, and unquoted YAML
booleans/ints are already `bool`/`int`. The string case is real but narrow:
**quoted** YAML scalars and string-producing templates. So the coercion is
not unnecessary — but it is not the broad safety net the docstring implies,
and `_to_int` in particular buys little while introducing W1's crash path.

Not a request to remove it. Worth a comment stating the *actual* narrow case
so a future reader doesn't over-trust it, and worth reconsidering `_to_int`
entirely if B1's "omit absent keys" fix lands (`auth.py:214` already does
`config.get('ssh_port') or _DEFAULT_SSH_PORT`, and `request_grant` does
`str(ssh_port)`, so a string port would work end-to-end without coercion).

## Nits (non-blocking)

- `test_only_auth_related_keys_are_added_to_module_args`
  (`test_shim.py:239-256`) is the proof for AC "only auth-related keys
  injected", but its `task_vars` omit `lagoon_api_endpoint` and
  `validate_certs`, so both `setdefault` branches at `__init__.py:89-92` are
  skipped and the assertion only ever observes `lagoon_api_token`. A case
  with endpoint + `validate_certs` + unrelated args all present would
  actually exercise the injection set.
- `_resolve_value` (`__init__.py:133-138`) uses `key in self._task.args`, so
  an explicit `lagoon_api_token: null` on the task wins over a set
  `task_vars` value and yields `None`. Arguably correct (explicit beats
  implicit) but undocumented and untested; one line of comment would settle
  intent.
- `_supports_async` is left at `ActionBase`'s `False`, so `async:`/`poll:` on
  a Lagoon task fails with "async is not supported". Consistent with most
  action plugins and out of the story's scope — noting only so it is a
  deliberate choice rather than an oversight.

## What passed review

Genuinely good, and worth recording so the next iteration does not regress it:

- **The §4 boundary holds.** `_STR_KEYS`/`_INT_KEYS`/`_BOOL_KEYS` enumerate
  only auth options — every entry maps to an `auth_argument_spec()` key. No
  resource-specific logic; nothing that makes sense for one module only.
  AC met.
- **`self._task.args` is never mutated.** `dict(self._task.args)` at
  `__init__.py:87`, proven by `test_task_args_dict_itself_never_mutated`.
- **The forbidden-import guard is not tautological.** Mutation-tested: adding
  `from ansible.errors import AnsibleError` to `plugins/module_utils/token.py`
  made `TestNoForbiddenImportsElsewhere` fail and correctly name the file.
  It walks the real tree. (Change reverted.)
- **Token/key redaction holds.** `AnsibleError(str(e))` only, no message
  construction from `config`; covered by
  `test_ansible_error_message_does_not_contain_token_value`.
- **Auth-failure short-circuit works for the `LagoonError` path** —
  `_execute_module` call count asserted zero in both
  `TestAuthFailurePropagation` cases.
- **Check mode is correctly left alone.** `ActionBase._supports_check_mode`
  is `True` and the shim adds no check-mode logic, exactly as the story
  requires.
- **Templating of `task_vars`-sourced values** is asserted on the mock
  templar call, not inferred, and the task-arg path correctly asserts
  `template` was *not* called.
- **`validate_certs` is read once**, not duplicated across the key tables —
  I checked specifically for that.
