# P3-S3a — Selection-shape rule: replace the raw depth limit

**Date:** 2026-09-04
**Parent plan:** [`docs/plans/v3-refactor.md`](./v3-refactor.md) §7.1
**Phase stories:** [`docs/plans/v3-phase3-stories.md`](./v3-phase3-stories.md)

**Amended by:** [P3-D18](./v3-phase3-stories.md), story **P3-S4a** — a bounded,

---

## Why this story exists

P3-S4 planning verified `project`'s argspec against
`schema/lagoon-2.33.0.graphql` and found six input fields with no readable
counterpart under the current depth-2 rule. Investigating why exposed that
the rule is measuring the wrong thing.

The rule's documented purpose is preventing v1's fan-out — `api_client.py::
project()` selected `environments { openshift { ... } kubernetes { ... } }`,
an unbounded object-list explosion. That is a real defect and must stay
forbidden. But the rule was written as a *depth* limit, and depth does not
distinguish fan-out from a bounded hop:

| Shape | Depth | Rows fetched | Current rule |
| --- | --- | --- | --- |
| `restrictions` — `[Restriction]`, enum list leaf | 2 | bounded | allowed |
| `autogeneratedRouteConfig { enabled }` — single object → scalar | 3 | **1, bounded** | **forbidden** |
| `openshift { id }` — single object → scalar | 3 | **1, bounded** | **forbidden** |
| `environments { id kubernetesNamespaceName }` — list → scalar leaves | 3 | **N, bounded by project** | **forbidden** |
| `environments { openshift { id } }` — list → object | 4 | **unbounded** | forbidden |

Rows 2–4 are all forbidden today, but only row 5 is v1's actual defect.
Row 4 in particular — "list every environment of this project, with a
couple of scalar fields each" — is one of the most common Lagoon reads
there is (it is how the v1 inventory plugin enumerates environments), and
the depth-2 rule blocks it outright with no decomposition available to
rescue it (see the next section). Forbidding rows 2–3 also costs real
correctness: `AddProjectInput.openshift` is `Int` but `Project.openshift`
is `Openshift`, so under the current rule the project module's deploy
target can be *set* but never *read* — every change to it would silently
never diff, and `diff_ignore` would be papering over a rule artefact
rather than a genuine absence of state.

### Correction to a P3-S4 planning finding

`restrictions` was initially grouped with the unreadable fields on the
reasoning that `[Restriction]` is a list. That was wrong. `Restriction` is
an **enum**, so `restrictions` is a scalar leaf at depth 2 and is already
legal under the existing rule. The flat-query rule forbids nested
*selection sets*, not list-typed leaves. `restrictions` is a normally
diffed field and needs no special handling.

## Finding: decomposition cannot replace bounded nesting

The first draft of this rule tried to route every nested field to
decomposition — a follow-up flat query per relation, rather than any
in-document nesting at all. That was tested against the SDL and rejected:
decomposition needs two things to exist for a given relation — a root
query returning the nested type, and a scalar key on the parent to drive
it. Measured on `Project`:

| Nested field | Type | Root query | Key on `Project` | Decomposable |
| --- | --- | --- | --- | --- |
| `organizationDetails` | `Organization` | `organizationById`, `organizationByName` | `organization: Int` | **Yes** |
| `environments` | `[Environment]` | none filtered by project (`environmentByName` takes a name you don't have yet; `environmentsByKubernetes` filters by deploy target; `allEnvironments` has no project argument at all) | none (`Environment.project` is itself an object, not a scalar) | **No** |
| `openshift` | `Openshift` | `allOpenshifts` (list-all only) | none | No |
| `kubernetes` | `Kubernetes` | `allKubernetes` (list-all only) | none | No |
| `autogeneratedRouteConfig` | `AutogeneratedRouteConfig` | none | none | No |
| `clone` | `ProjectClone` | none | none | No |

Decomposition works for 1 of 6. For `autogeneratedRouteConfig` and `clone`
there is no root query *at all* — they are reachable only as a
sub-selection of `Project`. For `openshift`/`kubernetes` there is no by-id
query and no key to correlate `allOpenshifts` against. **For
`environments` — "list a project's environments", one of the most common
reads in the whole API — there is no project-filtered root query and no
scalar key to filter client-side, because the only handle back to the
parent is itself a nested object.** Decomposition is a real option for
one relation on `Project` and is not available for the rest, including
the single most-needed one.

So the reframing of the *principle* is correct and is adopted below —
minimality ("fetch and send only what is required") is the real rule, and
it is stronger than a depth number. But decomposition is a
**complement**, applied only where a root query and a scalar key both
exist; the shape rule below has to stand on its own for everything else,
including ordinary list reads.

---

## The rule

Replacing §7.1's "maximum selection-set depth 2". The property that
actually matters is not depth but **expansion**: does one document's
response size grow with the number of related rows fetched *below* the
first hop. `restrictions` and `environments { id }` do not — one row (or
one bounded list) per field. `environments { openshift { id } }` does —
every environment triggers its own further fetch. That is the line:

> **Minimality.** A query selects only the fields the caller actually
> needs, and a mutation sends only the fields the caller actually set.
>
> **Bounded object hop.** A single-valued object field is permitted where
> every leaf beneath it is scalar or enum.
>
> **One collection hop.** A list-valued field is permitted where every
> leaf beneath it is scalar or enum. At most **one** such list selection
> per document.
>
> **No expansion below a list.** An object-typed field beneath a list
> selection is forbidden — that is v1's actual defect. A second list in
> the same document is forbidden — it is how v1's `projectInfo` document
> was rebuilt one field at a time even with every individual leaf legal.
> An object leaf beneath any nested selection (list or single-valued) is
> forbidden. There is no depth limit as such; these shape rules are what
> is enforced, and in practice they permit depth 3 and forbid depth 4 for
> every case in this SDL, but a future depth-3 case violating one of the
> shape rules above is still rejected regardless of its depth number.

Verified to classify every real case correctly, including the pair that
disproves depth as the actual criterion — `environments { id }` and
`environments { openshift { id } }` are the same depth (3) and get
opposite verdicts:

```
Project.restrictions                                    ALLOW  scalar-enum leaf, no nesting
Project.autogeneratedRouteConfig.enabled                ALLOW  bounded object hop
Project.autogeneratedRouteConfig.prefixes               ALLOW  bounded object hop, scalar-list leaf
Project.openshift.id                                    ALLOW  bounded object hop
Environment.project.name                                ALLOW  bounded object hop
Project.environments { id environmentType ... }        ALLOW  one collection hop, scalar leaves
Project.environments { openshift { id } }               DENY   object leaf beneath a list -- v1's defect
Project.deployTargetConfigs { deployTarget { name } }   DENY   object leaf beneath a list -- v1's defect
Project.environments {..} + envVariables {..}           DENY   two list selections in one document
Project.organizationDetails.owners                      DENY   object leaf beneath a bounded hop
v1 projectInfo (five object lists, one document)         DENY   object-below-list AND multi-list, both independently
```

Scope is bounded and small: 5 single-valued qualifying fields on
`Project`, 7 on `Environment`, 1 each on `Deployment` and `Task`, plus
whichever list-valued relation each info module actually needs — declared
explicitly in the registry (§2), never open-ended.

## Design

### 1. `client.py` — `build_query` must be able to emit a bounded hop

It currently cannot. `_FIELD_FORBIDDEN_RE = [{}\s(]` rejects any field
containing a brace or whitespace, so `'autogeneratedRouteConfig { enabled }'`
is refused outright — correctly, since that is the string-interpolation
path that would reintroduce injection.

Extend `fields` to accept a mapping entry alongside plain strings. The
same syntax serves both a bounded object hop and a bounded list hop —
`build_query` has no SDL access and cannot tell (and does not need to
tell) single-valued from list-valued; that distinction is the guard's job
(§2), applied to the reconstructed document, not to the call site's
arguments:

```python
LagoonClient.build_query(
    'projectByName',
    fields=['id', 'name', {'autogeneratedRouteConfig': ['enabled']},
            {'environments': ['id', 'environmentType',
                               'kubernetesNamespaceName']}],
    args={'name': 'String!'})
# -> query projectByName($name: String!) { projectByName(name: $name) {
#      id name autogeneratedRouteConfig { enabled }
#      environments { id environmentType kubernetesNamespaceName } } }
```

Constraints, all enforced in `build_query` itself:

- A mapping entry's key is validated by `_IDENTIFIER_RE` (stricter than
  the existing leaf check — a nesting field name must be a bare
  identifier, never brace-bearing text).
- Its value is a non-empty list of leaf names, each validated exactly as
  today's `fields` entries are.
- **One level only.** A mapping nested inside a mapping raises
  `LagoonConfigError`. The recursion the rule forbids is refused
  structurally, not merely discouraged.
- Braces are emitted by `build_query`, never accepted from a caller. This
  keeps the existing invariant that user data reaches the server only via
  `variables`.

`build_query` itself does **not** enforce the one-list-per-document cap or
the object-leaf-beneath-a-list prohibition — it has no SDL access, so it
cannot know which mapping keys are list-valued or which of a nested
mapping's leaves are objects. Both are the guard's job (§2). `build_query`
only guarantees the syntactic shape (one level, valid identifiers, no
caller-controlled braces); the semantic shape rules are checked
separately, against the SDL, by the test-time guard — never silently
skipped because `build_query` happened to accept the call.

Out of scope: the `args` type-string interpolation weakness. That is
P3-D8, explicitly deferred to Phase 8, and must not be opportunistically
fixed here.

### 2. The guard — classify shape, not just depth

`max_selection_depth()` is a text scanner with no schema knowledge, so it
cannot tell `autogeneratedRouteConfig` (single-valued object) from
`environments` (a list), and cannot by itself tell "an object leaf beneath
a list" from "a scalar leaf beneath a list" — both are depth 3 as raw text.
Two mechanisms, together:

**(a) An explicit permitted-nesting registry** in `query_depth.py`,
covering both hop kinds — a nested selection is permitted only if its
nesting field is declared here, whether it is single-valued or a list:

```python
#: Parent type -> nesting field -> (kind, permitted scalar/enum leaves).
#: kind is 'single' or 'list' -- checked against the SDL by the
#: conformance test below, never assumed from the call site.
PERMITTED_NESTED_SELECTIONS = {
    'Project': {
        'openshift': ('single', ('id', 'name')),
        'kubernetes': ('single', ('id', 'name')),
        'autogeneratedRouteConfig': ('single', (
            'enabled', 'allowPullRequests', 'prefixes',
            'disableRequestVerification')),
        'environments': ('list', (
            'id', 'name', 'environmentType',
            'kubernetesNamespaceName', 'deployType', 'autoIdle')),
    },
    ...
}
```

A nested document is permitted only if every nesting field it uses
appears here, with only the declared leaves selected beneath it, and at
most one `'list'`-kind entry used per document. Anything else is a
violation. Explicit and auditable — adding a nested selection, list or
single-valued, is a reviewable diff, not an emergent property of a
scanner.

**(b) An SDL conformance test** validating every registry entry against
`schema/lagoon-2.33.0.graphql`:

- the parent type and nesting field both exist;
- the declared `kind` matches the SDL's own list-ness for that field
  (`'list'` only for an actual `[T]`, `'single'` only for a bare `T`) —
  this is the check that stops a `'single'` entry silently drifting to
  cover a field that becomes a list in a future schema bump, or a
  copy-pasted entry declaring the wrong kind;
- every declared leaf exists on the nested type and is scalar or enum,
  never an object — this is what stops the registry drifting into
  permitting the exact fan-out the rule exists to forbid.

Parse the SDL with the standard library only — `re`, as the existing
`Makefile` `verify-mock` target and this planning work both did. `test-v3`
has no `graphql-core` and must not gain it (D3, P3-D6); a regex scan is
sufficient to answer "is this field list-typed" and "is this leaf a
scalar/enum".

The sweep in `collect_candidate_documents` keeps its current provenance
and vacuous-pass machinery unchanged. Only the pass/fail predicate
changes: `assert_flat_query` becomes shape-aware — parses the
reconstructed document's nesting structure, checks each nested field
against the registry (including the one-list-per-document cap and the
object-beneath-a-list prohibition), and gains an optional `parent_type`
so a call site can be checked against the right registry entry.

### 3. Decomposition doctrine

Documented in §7.1 and applied by later stories, not built here — there is
no consumer yet (`whoami_info` is flat; `project_info` arrives with the
breadth stories). Recording the rule now is what stops P3-S4 and the
generator inventing a different convention:

- A single-valued object with a real root query and a scalar key
  (`organizationDetails`, via `organizationById`/`organization: Int`)
  **should** be decomposed rather than nested, because it is separately
  addressable and often separately permissioned.
- A single-valued object with neither a root query nor a scalar key
  (`autogeneratedRouteConfig`, `clone`) uses a bounded object hop. There
  is no alternative — verified in the finding above.
- A list-valued relation decomposes into its own flat query **only when**
  a root query filtered by (or a scalar key resolvable to) the parent
  exists. Where it does not — `environments` is the concrete case: no
  root query takes a project filter, and `Environment.project` is itself
  an object, not a scalar to filter on client-side — the one-collection-hop
  rule (§ "The rule") is what makes the read possible at all, not a
  fallback of last resort.
- Either way, an object-typed field is never selected beneath a list, in
  or out of the registry. That prohibition is unconditional.

## Testing requirements

Shape classification, each proved against the real SDL where the case
exists in it:

1. `restrictions` (scalar-enum leaf, no nesting) — permitted. Pins the
   correction above; would have failed under the mistaken "lists are
   nested" reading.
2. `autogeneratedRouteConfig { enabled }` — permitted via the registry
   (bounded object hop).
3. `openshift { id }` — permitted (bounded object hop).
4. `environments { id environmentType kubernetesNamespaceName }` —
   **permitted** via the registry (one collection hop, scalar leaves).
   This is the single most important new test — the query this story was
   raised over — and it must be proved against the real SDL, not a
   synthetic fixture, since it is exactly the case the original draft of
   this rule got wrong.
5. `environments { openshift { id } }` — **rejected**: an object leaf
   beneath a list. Same depth (4) as case 4 is depth-3 — the pair (4, 5)
   together is the discriminating proof that the rule measures expansion,
   not depth: two documents differing only in whether the leaf beneath
   the list is a scalar or an object, with opposite verdicts.
6. `environments { id } ` + `envVariables { name }` in the same document
   — **rejected**: two list selections, even though each alone (per case
   4's shape) would be permitted individually. Proves the one-list cap is
   enforced across the whole document, not per-field.
7. `organizationDetails { owners }` — **rejected**: object-typed leaf
   beneath a bounded single-valued hop.
8. `V1_PROJECT_INFO_QUERY` — still rejected, and for **both** reasons
   independently (object-beneath-list on `environments { openshift {...} }`,
   and five list selections in one document) — assert on the specific
   violation the guard reports, not merely that it raises, so a future
   change that accidentally fixes one reason doesn't silently leave the
   other unexercised.
9. A nested document whose nesting field is **absent from the registry**
   — rejected, proving the allowlist is load-bearing rather than
   decorative, for both a single-valued and a list-valued absent field.
10. Registry/SDL conformance: every entry's parent type and nesting field
    exist; the declared `kind` (`'single'`/`'list'`) matches the SDL's
    actual list-ness for that field; every declared leaf exists and is
    scalar/enum.
11. A deliberately bad registry entry, tested two ways, each making test
    10 **fail** — the guard-passes-for-the-wrong-reason lesson from P2-S7
    and P3-S9:
    - a list-valued field wrongly declared `kind='single'` (or vice
      versa);
    - an object-typed leaf listed among the permitted leaves.
    Assert the failure with a temporarily patched registry, not by
    committing a broken one.

`build_query` nesting:

12. Mapping entry emits `field { leaf leaf }`, exact string equality —
    proved for both a single-valued-shaped and a list-shaped call
    (`build_query` itself does not distinguish them; both must produce
    the same syntactic shape).
13. Mapping nested inside a mapping raises `LagoonConfigError`.
14. A brace/whitespace-bearing nesting key raises `LagoonConfigError`.
15. An empty leaf list raises `LagoonConfigError`.
16. Existing flat call sites produce byte-identical output to before —
    this change is additive. Assert against the literal strings already
    in `test_query_depth.py`'s `TestBuildQueryIntegration`.

End-to-end, per the phase document's cross-story-regression warning:

17. The full sweep over `plugins/` stays green, and the vacuous-pass
    guard still fires (it must keep finding `whoami_info`'s call site).

## Review focus

- Is the rule genuinely shape-based, or is it a depth ceiling with extra
  steps? The discriminating question: do `environments { id }` and
  `environments { openshift { id } }` — same field, same depth — get
  opposite verdicts?
- Is the one-list-per-document cap actually enforced across the whole
  document, or only checked per selected field (which would let
  `environments {..} envVariables {..}` slip through)?
- Does the registry conformance test actually fail on a bad entry — a
  wrong `kind` and a smuggled-in object leaf, tested separately — or does
  it pass vacuously because the SDL regex silently matches nothing?
  Confirm by patching in a known-bad entry for each.
- Can any caller get a brace into a query document through the new
  mapping form — via the nesting key, a leaf name, or a nested mapping?
- Is `build_query`'s flat output byte-identical? A whitespace drift here
  would break P3-S9's byte-for-byte gate before it is even written.
- Is the deferred `args` hardening (P3-D8) still deferred, not quietly
  half-fixed?
- Does `V1_PROJECT_INFO_QUERY`'s rejection actually exercise both
  violations it contains, or does the guard stop at the first and leave
  the multi-list defect untested?

## Decisions to record in `v3-phase3-stories.md`

| # | Item | Decision |
| - | ---- | -------- |
| **P3-D10** | **Depth limit replaced by a selection-shape rule** | The depth-2 limit forbade bounded hops (`openshift { id }`, `autogeneratedRouteConfig { enabled }`, and ordinary list reads such as `environments { id, kubernetesNamespaceName }`) that are structurally unlike v1's fan-out defect, while permitting nothing it needed to. Replaced by: minimality; a bounded object hop where every leaf is scalar/enum; one collection (list) hop per document where every leaf is scalar/enum; no object leaf beneath any nested selection; no second list selection in the same document. There is no depth number as such — these shape rules are what is enforced, and they happen to permit depth 3 and forbid depth 4 throughout this SDL, but the classification never consults depth directly. Enforced by an explicit permitted-nesting registry (declaring each nesting field's kind — single or list — and its permitted leaves) plus an SDL conformance test, since the guard's text scanner cannot infer list-ness or leaf-object-ness on its own. |
| **P3-D11** | **Decomposition complements the shape rule; it cannot replace it, including for ordinary list reads** | An earlier draft of this rule routed every relation to decomposition (a follow-up flat query per relation) instead of any in-document nesting. Measured against the SDL and withdrawn: of `Project`'s single-valued object fields, only `organizationDetails` has both a root query and a scalar key. `autogeneratedRouteConfig` and `clone` have **no root query at all**. `openshift`/`kubernetes` have only list-all queries and no key to correlate on. Most importantly, **`environments` — listing a project's environments, one of the most common reads in the API — has no project-filtered root query and no scalar key to filter by client-side**, because `Environment.project` is itself an object. Doctrine: decompose only where a root query and a scalar key both exist for that relation; everything else, including `environments`, is read via the shape rule's bounded object/collection hops, never assumed away as "always decomposable". |
| **P3-D12** | **`restrictions` is a legal leaf; list-typed does not mean nested** | Corrects a P3-S4 planning finding. `Restriction` is an enum, so `[Restriction]` is a scalar-list leaf with no selection set at all — legal under both the old and new rule. The rule forbids nested selection *sets* and object leaves, never a list of scalars/enums selected as a plain leaf. `restrictions` is diffed normally. |
| **P3-D13** | **`openshift`/`kubernetes` become diffable, not `diff_ignore`d** | `AddProjectInput.openshift` is `Int` while `Project.openshift` is `Openshift`. Under the depth-2 rule the deploy target was settable but unreadable, so `project` would have had to `diff_ignore` it and silently never detect a change. Under P3-D10 the module reads `openshift { id }` (a bounded object hop) and diffs the id. `diff_ignore` is reserved for fields with no readable state at all, not for rule artefacts. |
| **P3-D14** | **One list selection per document** | v1's `projectInfo` nested five object lists (`environments`, `deployTargetConfigs`, plus others) into one document; the object-beneath-list prohibition alone blocks its actual per-row expansion, but a cap is still needed so a future document cannot reassemble `projectInfo`'s breadth — five *scalar-leaf* lists in one read — even with every individual leaf legal under P3-D10. A composite info module wanting both `environments` and `envVariables` issues two reads, not one; each is separately cacheable and separately permissioned, which is the same reasoning P3-D2 already applied to `env_variable`'s own list read. |

Remaining genuinely write-only on `project` after this story: `addOrgOwner`
(a creation-time actor flag whose effect is only visible via
`organizationDetails { owners }` — an object leaf beneath a bounded hop,
forbidden) and `disableRequestVerification` only if it proves absent from
`AutogeneratedRouteConfig` on inspection. The five autogenerated-route
fields that motivated this story become fully diffable via a bounded
object hop, and `environments`-shaped reads become possible for the first
time via the collection hop.

## Commit

```
feat(v3): replace the query-depth limit with a selection-shape rule

The depth-2 limit measured the wrong property. It forbade bounded
object hops (openshift { id }, autogeneratedRouteConfig { enabled })
and ordinary list reads (environments { id, kubernetesNamespaceName })
that fetch one row or one bounded list and are structurally unlike
the unbounded per-row fan-out the rule exists to prevent -- one of
the most common Lagoon reads, "list a project's environments", was
unreachable under the old rule with no decomposition able to rescue
it (no root query filters environments by project, and
Environment.project is itself an object, not a scalar to filter on).

The rule is now shape-based, not depth-based: a bounded object hop or
a single collection (list) hop, each with scalar/enum leaves only; no
object leaf beneath any nested selection; no second list selection in
the same document. Enforced by an explicit permitted-nesting registry
(declaring each nesting field's kind and permitted leaves) plus an
SDL conformance test, because the guard's text scanner cannot infer
list-ness or leaf shape by itself. v1's five-list, object-nested
projectInfo document stays rejected, for both reasons independently.

build_query grows a mapping form serving both hop kinds -- it has no
SDL access and does not need one, since kind/shape enforcement is the
guard's job, not the client's. Braces are still emitted only by
build_query, never accepted from a caller, and nested mappings are
refused structurally.

Decomposition is documented as the complement, not the replacement:
measured against the SDL, only one of Project's single-valued object
relations has both a root query and a scalar key, and environments --
the relation motivating this change -- has neither.
```
