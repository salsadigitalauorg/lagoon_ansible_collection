## Why this document exists

P3-S4 planning verified the `project` argspec and read query against
`schema/lagoon-2.33.0.graphql` and `resource.py`/`lookup.py` as committed, and
found four things the phase document did not account for. Each is a deviation
from `v3-refactor.md`/`v3-phase3-stories.md` as written (per "How to work

this produces (P3-D5), so getting these settled before a line of `project.py`
is written is the point.

## Finding 1 — the guard cannot pass a legal bounded-hop read as written

`project`'s read needs three bounded object hops (`openshift { id }`,
`kubernetes { id }`, `autogeneratedRouteConfig { ... }`) to make the
create-only/update-only fields that target them diffable at all (P3-D13).
Reproduced against the real guard and client code:

1. `tests/unit/plugins/module_utils/test_query_depth.py`'s sweep calls
   `assert_flat_query(document, source=source)` with **no `parent_type`**
   (`query_depth.py:476`, the sweep's own call at line ~476 in
   `TestSweep.test_sweep_runs_clean_against_current_plugins_tree`).
   `classify_selection_shape` then does `registry.get(None, {})` → `{}` →
   every nested selection is `undeclared_nesting`, including ones legally
   declared in `PERMITTED_NESTED_SELECTIONS['Project']`. Reproduced directly:
   the same document classifies as a violation with no `parent_type` and
   passes with `parent_type='Project'`.
2. If the read's `fields` list is a module-level constant (the natural way
   to write it, and what `whoami_info.py` already avoids only because its
   query is flat), `_resolve_build_query_args` → `_literal_from_ast` cannot
   resolve a `Name` reference and returns `UNRESOLVED_BUILD_QUERY`. The sweep
   then `continue`s past it with no depth/shape check at all — reproduced:
   `fields=_FIELDS` resolves to the unresolved placeholder. This is a
   vacuous pass in the P2-S7/P3-D6 sense: the guard would not have caught a
   nested-and-wrong read either.

Neither defect is specific to `project` — every future bounded-hop read hits
both. Fixed once, in the guard, not worked around per-module.

## Finding 2 — the real field sets, and two fields with no readable state

Computed against the vendored SDL (not assumed from §6's example):

- `AddProjectInput`: 36 fields. `UpdateProjectPatchInput`: 39 fields. Union:
  **42**. `create_only = [id, organization, addOrgOwner]`,
  `update_only = [autogeneratedRoutes, autogeneratedRoutesPullrequests,
  autogeneratedRoutePrefixes, autogeneratedPathRoutes,
  disableRequestVerification, restrictions]` — both match P3-D1 exactly.
- Of the 42: 34 are plain scalar/enum leaves on `Project`. `openshift` and
  `kubernetes` are `Int` on input, `Openshift`/`Kubernetes` object types on
  output — read via a bounded hop (`{ id }`), diffed per P3-D13. Four of the
  six update-only fields map onto `AutogeneratedRouteConfig`'s own fields
  (`enabled`, `allowPullRequests`, `prefixes`, `disableRequestVerification`)
  and are readable via that same bounded hop.
- **`addOrgOwner`** (create-only) has no readable counterpart anywhere: its
  only visible effect is `Organization.owners { ... }`
  (`[OrgUser]`, SDL:1397), an object list beneath `organizationById`'s
  bounded hop on a *different* resource's read — out of scope for `project`.
- **`autogeneratedPathRoutes`** (update-only) maps to
  `AutogeneratedRouteConfig.pathRoutes: [AutogeneratedPathRoute]`
  (SDL:1202) — an object-list leaf nested beneath the `autogeneratedRouteConfig`
  hop, depth 4. Forbidden under P3-S3a as committed (`object_leaf_beneath_nesting`,
  reproduced) and unreachable by decomposition (`AutogeneratedPathRoute` has
  no root query in this SDL). See P3-D18 below — this one gets fixed, not
  documented as unreadable, because all three of its leaves are scalar.
- `privateKey` **is** readable (`Project.privateKey: String`, SDL:687) but is
  deliberately excluded from the read selection anyway — see P3-D17.

## Finding 3 — `organization`'s only non-deprecated convergence path is destructive

`organization` (create-only, per P3-D1) is readable: `Project.organization:
Int` (SDL:661) is a plain scalar, contrary to this document's own earlier
assumption that create-only implies unenforceable idempotency. Checked
against the SDL for a mutation that could converge a mismatch:

- `addExistingProjectToOrganization(input: AddProjectToOrganizationInput):
  Project` is `@deprecated(reason: "Use
  bulkImportProjectsAndGroupsToOrganization instead")` (SDL:3184).
- `removeProjectFromOrganization(input: RemoveProjectFromOrganizationInput):
  Project` is not deprecated, but its own SDL description reads: "this will
  return the project to a state where it has no groups or notifications
  associated to it" (SDL:3186-3188) — destructive far beyond the one field
  being diffed.
- `bulkImportProjectsAndGroupsToOrganization`, the suggested non-deprecated
  replacement, has **no corresponding `input` type declared anywhere in this
  SDL** — unreachable from a generated module today.

So `project.py` must not attempt to converge a mismatched `organization` by
calling either mutation. See P3-D16.

Per P3-D3's chain: (1) input SDL description, (2) same-named output-type

## Decisions

### P3-D15 — `GraphQLNonNull` on the create input is a create-time check, not a blanket argspec `required`

§6.1 rule 2, applied literally to a resource whose create and update share
one argspec, would make `git_url`/`production_environment` argspec-`required`
— which then also requires them for `state: absent` and for an update
touching one unrelated field. One flat argspec serves create, update *and*
delete; a create-time-only requirement cannot live in `required: true`.

**Decision:** only `name` (the resource's own read/delete key) is
argspec-`required`. `git_url` and `production_environment` — `AddProjectInput`'s
other two `NonNull` fields — are enforced in the create branch only, raising
`LagoonConfigError` naming the missing option(s), before `addProject` is
ever called. The generator must derive "argspec-required" from the read key
alone, and "create-required" from the create mutation's own `NonNull` set,
as two distinct checks — never one.

### P3-D16 — create-only enforcement is driven by readability, not by a single rule

P3-D1 says a create-only field supplied against an existing resource raises
`LagoonConfigError`, full stop. Finding 3 shows this is too strong for a
readable field, and Finding 2 shows one create-only field is unreadable.
Resolved into three mechanical clauses, none of them resource-specific:

- **Readable and equal to current state** → treated as a no-op for that
  field. A create playbook re-run with `organization:` set stays idempotent.
- **Readable and different from current state** → `LagoonConfigError`,
  naming the current value, the requested value, and (for `organization`
  specifically) `removeProjectFromOrganization` /
  `bulkImportProjectsAndGroupsToOrganization` as the supported way to move a
  project between organizations — never attempted automatically, per
  Finding 3.
- **Unreadable** (`addOrgOwner`) → `LagoonConfigError` unconditionally when
  supplied against an existing resource, because there is no state to prove
  convergence against. Documented on the option: has no effect on `state:
  present` against an existing project.

This is fully mechanical from `create_only` plus the read field set — the
generator needs no per-field table, only "is this create-only field in
`fields`".

### P3-D17 — `private_key` is never read

`Project.privateKey` is a readable scalar (SDL:687), but a resource module
that re-fetches SSH key material every run merely to diff it is an
unjustified secret-handling cost (ISM-0459 — minimise handling of key
material) with no idempotency benefit strong enough to justify it: Lagoon
generates a key pair server-side if none is supplied, so "diffing" it mostly
means detecting server-generated churn, not a caller-intended change.

**Decision:** `private_key` stays in `fields` (for `RETURN` docs) and in
`no_log_fields`, but is excluded from the actual read selection set. Its
diff always reports via `changed_no_log_fields` when supplied on `present`
against an existing project (matching P3-D7's no_log diff shape exactly —
changed/unchanged fact only), and the create/update closures send it
whenever supplied. Documented on the option as write-only: this module
cannot detect drift in a private key already stored server-side.

### P3-D18 — bounded scalar-leaf list beneath a single-valued object hop (amends P3-S3a)

`autogeneratedRouteConfig { pathRoutes { fromService toService path } }` is
depth 4 and violates P3-S3a's "no object leaf beneath any nested selection"
as committed — reproduced: `max_selection_depth` = 4,
`classify_selection_shape` raises `object_leaf_beneath_nesting`, and
`LagoonClient.build_query` structurally refuses a mapping nested inside a
mapping. But `pathRoutes` is bounded by one project's own route
configuration (routinely 0–2 entries, not a per-row expansion over a
collection) and every one of its three leaves (`fromService`, `toService`,
`path`) is a plain scalar — it is not v1's defect, it is the same "bounded
hop, scalar leaves only" property the rest of P3-S3a already permits, one
level deeper because it sits beneath a single-valued hop rather than at the
top level.

**Decision:** extend the shape rule and its registry, in a **separate
commit landing before P3-S4** (see P3-S4a below), never folded into the
`project` module's own commit:

- A registry leaf entry under a `'single'`-kind nesting field may itself be
  a single-entry mapping `{field: ('list', (leaf, ...))}` instead of a plain
  string, declaring a bounded scalar-leaf list one level beneath that hop.
- This nested-list form is **never permitted beneath a `'list'`-kind nesting
  field** — that recursion is exactly v1's defect and stays unconditionally
  forbidden. Only single-valued → list is new; list → anything-but-scalar
  stays exactly as forbidden as before.
- It counts toward the document's one-list-selection cap (P3-D14) — a
  document combining `autogeneratedRouteConfig { pathRoutes { ... } }` with
  a top-level `environments { ... }` read is still rejected.
- `client.py`'s `_render_field` gains support for a leaf that is itself a
  single-entry mapping of plain strings, one level deeper than today,
  still refusing a third level and still emitting braces only itself, never
  from caller-supplied text.
- `query_depth.py`'s registry/SDL-conformance check is extended to validate
  the nested form the same way as the top-level form: parent/field exist,
  declared kind matches the SDL's actual list-ness, every declared leaf is
  scalar/enum.

This changes the phase document's shape rule (P3-D10) from "bounded object
hop OR one collection hop, one level, scalar/enum leaves" to "...scalar/enum
leaves **or one further bounded scalar-leaf list beneath a single-valued
hop**" — still no expansion beneath any list, still one level of new
nesting, still forbidden to recurse. It does not touch decomposition
doctrine (P3-D11) or the P3-D12/D13/D14 corrections, all of which stand as
committed.

### Design

`plugins/modules/project.py`, same structural shape as `whoami_info.py`
(`run_module(module)` taking a params-bearing object, `main()` wiring
`AnsibleModule` + `auth.auth_argument_spec()`), extended with:

- `state: present|absent` (default `present`).
- All 42 options from the `AddProjectInput` ∪ `UpdateProjectPatchInput`
  union (Finding 2's table), each `no_log=True` only for `private_key`,
  `choices` populated for `availability` (3) and `restrictions` (5, as a
  list), `type='dict'`/`options=` for `autogenerated_path_routes`.
- Read: `projectByName(name:)` returning the 34 plain scalar leaves plus
  `openshift { id }`, `kubernetes { id }`, and
  `autogeneratedRouteConfig { enabled allowPullRequests prefixes
  disableRequestVerification pathRoutes { fromService toService path } }`
  — omitting `privateKey` per P3-D17. The read closure flattens each hop
  into the wire-field namespace `resource.py` expects (`openshift` → its
  `id`, the four ARC scalar fields → their input names, `pathRoutes` → a
  list of dicts keyed the same as `autogenerated_path_routes`'s `options`).
- Create-time-only requiredness (P3-D15): before calling `addProject`,
  raise `LagoonConfigError` if `git_url` or `production_environment` is
  unset — not `required: True` on the argspec.
- Create-only enforcement (P3-D16): before calling `addProject` when
  `current is not None` (i.e. an update path is about to run but a
  create-only field was also supplied), apply the three clauses per field
  in `create_only`.
- `private_key` excluded from the read, reported only via
  `changed_no_log_fields` (P3-D17).
- Update-path wire-shaping (`{id, patch: {...}}`) hand-written inline, as
  the original P3-S4 already specified — this story still does not import
  anything from `codegen/`.
- Delete: `deleteProject(input: {project: <name>})`, `fields=[]`, matching
  `DeleteProjectInput.project: String!` — verified against the SDL
  (`DeleteProjectInput { project: String! }`, SDL:2407), not assumed from
  the mutation name.

`plugins/action/project.py` — one-line subclass, identical shape to
`plugins/action/whoami_info.py`.

Guard fixes (Finding 1), same commit:

- `assert_flat_query`'s sweep call site gains `parent_type` resolution:
  given a reconstructed document, extract the root field name and resolve
  its return type via `sdl_object_type_fields(sdl_text, 'Query')` /
  `..., 'Mutation')`, passing the result through as `parent_type`. Falls
  back to `None` (today's behaviour) only when the root field cannot be
  resolved to either root type — never silently narrows coverage for a
  document that *can* be resolved.
- `_literal_from_ast`/`_resolve_build_query_args` (or a wrapper around
  them used by `collect_candidate_documents`) resolve a bare `Name`
  reference to a module-level string/list constant already collected by
  `_module_and_class_level_assigns`, so `fields=_PROJECT_READ_FIELDS`
  reconstructs a real document instead of `UNRESOLVED_BUILD_QUERY`. Falls
  back to unresolved (not a hard failure) for anything not a plain
  module-level name — a computed expression stays honestly "not checked".

### Testing requirements

Mirrors P3-S3's state-transition matrix through the actual module
(`run_module`, mocked `LagoonClient.execute`):

1. Create: no existing project, `state: present` with `git_url`/`name`/
   `production_environment` → `addProject` called with exactly those wire
   field names (camelCase), `changed=True`.
2. Create missing a `NonNull` field (e.g. no `git_url`) → `LagoonConfigError`
   naming `git_url`, no mutation call — proves P3-D15, not just that
   `required: True` would have caught it (it must not be `required: True`).
3. Update: existing project, one field differs (`auto_idle`) →
   `updateProject` called with `{id: <id>, patch: {autoIdle: <value>}}` —
   exact nested shape asserted.
4. Update touching only `openshift`/`kubernetes`/one ARC field → the bounded
   hop's read value participates in the diff and the mutation payload uses
   the flat input name (`openshift`, not `openshift.id`).
5. `pathRoutes` update: existing project with different
   `autogenerated_path_routes` → diff computed from the nested read,
   `updateProject` patch carries the list of dicts.
6. No-op: existing project, no field differs (including `pathRoutes`
   compared structurally) → no mutation call, `changed=False`.
7. Delete: existing project, `state: absent` → `deleteProject` called with
   `{project: <name>}`.
8. `check_mode` variant of 1, 3, 7 — zero mutation calls, identical
   `changed`/`diff`.
9. `organization` equal to current value, existing project → no-op for that
   field specifically (mixed with another changed field to prove it doesn't
   block the rest of the update).
10. `organization` different from current value, existing project →
    `LagoonConfigError` naming current and requested values, no mutation
    call.
11. `add_org_owner` supplied, existing project → `LagoonConfigError`, no
    mutation call (unconditional — P3-D16's unreadable clause).
12. `private_key` supplied, existing project, value differs from... there is
    nothing to compare against (never read) → reported via
    `changed_no_log_fields` only, `privateKey` sent in the update payload,
    never appears in `before`/`after`, and the read document built by
    `run_module` is asserted to omit `privateKey` entirely.
13. `run_module` passes with no action shim involved (P2-S6's boundary
    proof, repeated here).
14. Guard-fix regression: a fixture module with a nested-but-undeclared

    literal), is now caught by the sweep — proving Finding 1's clause 2 fix
    turns a prior vacuous pass into a real check, not just that clause 1's
    `parent_type` fix works on an inline literal.

Three deviations from the allowlist's create-only/update-only model,
found verifying it against the real SDL: organization is a readable
scalar (Project.organization: Int) so its create-only enforcement is

git_url/production_environment are AddProjectInput's other NonNull

required=True -- the same argspec also serves update and delete,
