**Date:** 2026-09-03
**Parent plan:** [`docs/plans/v3-refactor.md`](./v3-refactor.md) §9 Phase 3
**Branch:** `3.x`
**Status:** Ready for implementation

## How to work these stories

1. Stories are executed **in order**. Each depends on the ones before it.
2. Each story produces **exactly one commit**. Do not batch stories into one commit.
3. After each commit, hand the commit SHA to the `review` agent. Iterate on that
   story's commit (amend or follow-up fixup, reviewer's choice) until the reviewer
   is satisfied. Only then start the next story.
4. Every story below carries its own acceptance criteria and verification commands.
   A story is not complete until its verification commands pass locally.
5. If a story's implementation reveals that the parent plan is wrong, **stop and
   raise it** rather than silently deviating. Record the deviation in the story's
   commit body. Phase 2's breakdown did this three times (P2-D9/D10 plus the
   fork-model correction); Phase 3's own breakdown already did it four times
   before a single line of code was written — see the decisions table below.
6. **P3-S4 is the load-bearing story in this phase.** It hand-writes `project`
   against `resource.py`/`lookup.py` with no generator involved, and every
   later story's gate is "reproduce this file byte-for-byte". If P3-S4 is
   wrong, everything after it inherits the mistake silently. Route it through
   an extra review pass focused only on §7.4's flow, independent of the
   generator work that follows.
7. **P3-S3 (`resource.py`) is the second most load-bearing story.** It is the
   real engineering effort the parent plan flags in §7.4 — `check_mode` and
   `--diff` correctness are the acceptance bar for "idiomatic Ansible", and
   v1 has no equivalent to port from. Budget review time accordingly.
8. Two process lessons from Phase 2 apply doubly here, because this phase
   generates code at far larger scale than anything reviewed by hand so far:
   - **A green suite can hide a cross-story regression** if a test asserts
     on an intermediate value instead of the value at the end of the real
     call path (P2-S6/P2-S7's `BatchMode` finding). Every story below that
     touches a value another story's default depends on carries an explicit
     end-to-end assertion, not just a unit-level one.
   - **A guard test can pass for the wrong reason** (P2-S7's vacuous-pass
     finding). P3-S9's byte-identical reproduction gate is itself exactly
     this kind of guard — its own acceptance criteria include proving it
     fails when it should, not just that it passes.

These correct parts of `v3-refactor.md` §6/§6.1/§9 against the real vendored
SDL (`schema/lagoon-2.33.0.graphql`) and are also applied as amendments to
the parent plan itself.

| # | Item | Decision |
| - | ---- | -------- |
| **P3-D1** | **Create/update asymmetry** | `addProject(input: AddProjectInput!)` is flat; `updateProject(input: UpdateProjectInput!)` is `{id: Int!, patch: UpdateProjectPatchInput!}` — one level of nesting the parent plan's §6 example did not account for. Field sets diverge too (create-only: `id`, `organization`, `addOrgOwner`; update-only: `restrictions`, `autogeneratedRoutes`, `autogeneratedRoutePrefixes`, `autogeneratedPathRoutes`, `autogeneratedRoutesPullrequests`, `disableRequestVerification` on `project`; similar shape on `environment`). The generator presents **one flat argspec** to the user; a per-mutation wire-shaping layer (`codegen/wire.py`, P3-S6) builds the correct wire payload for whichever mutation is being called and raises a named `LagoonConfigError` if a create-only field is supplied against an existing resource, or an update-only field against a new one — never silently dropped, never forwarded to the server to fail there instead. |
| **P3-D2** | **Gate resource selection** | `env_variable`'s real input types (`EnvVariableByNameInput`, `DeleteEnvVariableByNameInput`) take `project`/`environment` as **name strings**, not ids — it needs no lookup at all, contradicting the parent plan's original `lookups: [project_id, environment_id]`. Kept in the gate set anyway, repurposed: it proves the list-read + client-side-filter path (`getEnvVariablesByProjectEnvironmentName` returns `[EnvKeyValue]`, not a single record) and enum-case diffing (`scope` is the `EnvVariableScope` enum, upper-case, on input; plain `String` on output). `environment` becomes the resource proving both lookup types end to end (`AddEnvironmentInput.project: Int!` on create, `updateEnvironment(id: Int!, ...)` on update) — the role the parent plan had originally assigned to `env_variable`. |
| **P3-D3** | **Description fallback chain** | Measured against the gate resources: `AddProjectInput` 0/36 fields with an SDL description, `UpdateProjectPatchInput` 0/39, `EnvVariableByNameInput` 0/6. `antsibull-docs` fails on any undocumented option, so the parent plan's §6.1.5 ("source option help from SDL descriptions") cannot close the gate as written. Fallback chain, each step only filling what the previous left undescribed: (1) the input type's own SDL description; (2) the same-named field's description on the mutation's output type (covers 29/36 on `project`, 10/14 on `environment`, but 0/6 on `env_variable` — `EnvKeyValue`'s fields are undescribed too); (3) an `allowlist.yml` per-module `descriptions:` override block; (4) **fail the build** if any option is still undescribed after all three. Docs lint must never be the first place a coverage gap is discovered — `make generate` fails first, locally, before a commit exists to review. |
| **P3-D4** | **Phase 3/4 boundary** | The parent plan's original split — generator-only in Phase 3, `resource.py`/`lookup.py` deferred to Phase 4 — cannot close the Phase 3 gate as written: that gate requires "`check_mode`/`--diff` are correct", and that correctness lives entirely in the read-diff-mutate engine the old Phase 4 owned. `resource.py` and `lookup.py` move into this phase (P3-S2/P3-S3), proven together with the generator on three resources — the same walking-skeleton shape P2-D5 used for `whoami_info`. The old Phase 5 ("generate the core set") folds into this phase's later breadth stories (P3-S10/S11/S12); Phase 5 is retired, Phases 6/7/8 keep their existing numbers. |
| **P3-D5** | **Golden-target technique** | `project` is hand-written first (P3-S4), directly against `resource.py`/`lookup.py`, with no generator involved — proving the runtime engine on a real resource before any code generates anything. The generator's own acceptance criterion (P3-S9) is then "regenerate `project` and diff it against P3-S4's committed file — zero difference". This is a stronger check than a hand-reviewed "looks about right"; it makes the generator's correctness mechanically verifiable rather than a matter of read-through confidence. |
| **P3-D6** | **`codegen/` test isolation** | `codegen/` depends on `graphql-core` (D3: generator-only, never a runtime dependency). A new `codegen-v3` compose service runs `codegen/`'s own `pytest` suite in a container that never touches the `test-v3`/`ansible-test` environment, so `graphql-core` has no path into the environment that also runs the shipped collection's unit tests. This keeps D3 structurally enforced (a forbidden-import AST test *inside* `test-v3` would prove `graphql-core` isn't imported by `plugins/`, but would not prove it can't reach that environment at all — a separate container does). |
| **P3-D7** | **`no_log` on `value`** | `env_variable`'s `value` option is `no_log: true` (Lagoon environment variables routinely hold secrets). Ansible's default `no_log` behaviour on `--diff` would replace the *entire* diff for that field with `VALUE_SPECIFIED_IN_NO_LOG_PARAMETER`, which would fail the Phase 3 gate's own "`--diff` is correct" criterion by making the diff useless for the one field most likely to actually change. Resolved explicitly (owner's decision, not Ansible's default): the diff reports **changed/unchanged only** for `value` — the boolean fact of a difference, never either side's plaintext, on both the check-mode preview and the real-run result. See P3-S11 for the mechanism. |
| **P3-D8** | **`client.py` args-interpolation hardening deferred to Phase 8** | P2-S7's review found `LagoonClient.build_query()` interpolates the `args` dict's GraphQL *type* strings unvalidated (only argument *names* are checked) — reproduced producing a depth-3 document from a crafted type string, and a `"` in a field name crashing the depth scanner instead of failing cleanly. `args` values are generator-controlled from this phase onward, not user-controlled, so the risk is latent rather than exploitable through any code path this collection ships. Explicitly deferred to Phase 8 alongside the collection's other pre-release security hardening (§11) — not fixed opportunistically mid-Phase-3, so the generator's early stories aren't blocked on an unrelated `client.py` change. |
| **P3-D9** | **Enum-case diffing** | `EnvVariableByNameInput.scope: EnvVariableScope` is an upper-case enum (`BUILD`, `RUNTIME`, `GLOBAL`, `CONTAINER_REGISTRY`, `INTERNAL_CONTAINER_REGISTRY`); `EnvKeyValue.scope: String` — the read side — is a plain string with no enforced case. v1's `env_variable` action compared `.lower()` on both sides (`api/plugins/action/env_variable.py:112`). `resource.py`'s diff step needs a declared per-field case-normalisation hook (`enum_case_normalise: {scope: upper}` in the allowlist) or every run against a real API reports a spurious change on `scope` even when nothing changed. |
| **P3-D10** | **Depth limit replaced by a selection-shape rule** | Raised during P3-S4 planning, resolved in **P3-S3a** (inserted before P3-S4 — see `docs/plans/2026-09-04-p3-s3a-nesting-rule.md`). The depth-2 limit forbade bounded hops (`openshift { id }`, `autogeneratedRouteConfig { enabled }`, and ordinary list reads such as `environments { id, kubernetesNamespaceName }`) that are structurally unlike v1's fan-out defect, while permitting nothing it needed to. Replaced by: minimality; a bounded object hop where every leaf is scalar/enum; one collection (list) hop per document where every leaf is scalar/enum; no object leaf beneath any nested selection; no second list selection in the same document. There is no depth number as such — these shape rules happen to permit depth 3 and forbid depth 4 throughout this SDL, but classification never consults depth directly. Enforced by an explicit permitted-nesting registry (declaring each nesting field's kind — single or list — and its permitted leaves) plus an SDL conformance test, since the guard's text scanner cannot infer list-ness or leaf-object-ness on its own. Also recorded as `v3-refactor.md` D21. |
| **P3-D11** | **Decomposition complements the shape rule; it cannot replace it, including for ordinary list reads** | An earlier draft of P3-S3a routed every relation to decomposition (a follow-up flat query per relation) instead of any in-document nesting. Measured against the SDL and withdrawn: of `Project`'s single-valued object fields, only `organizationDetails` has both a root query and a scalar key. `autogeneratedRouteConfig` and `clone` have **no root query at all**. `openshift`/`kubernetes` have only list-all queries and no key to correlate on. Most importantly, **`environments` — listing a project's environments, one of the most common reads in the API — has no project-filtered root query and no scalar key to filter by client-side**, because `Environment.project` is itself an object. Doctrine: decompose only where a root query and a scalar key both exist for that relation; everything else, including `environments`, is read via the shape rule's bounded object/collection hops. |
| **P3-D12** | **`restrictions` is a legal leaf; list-typed does not mean nested** | Corrects a P3-S4 planning finding. `Restriction` is an enum, so `[Restriction]` is a scalar-list leaf with no selection set at all — legal under both the old and new rule. The rule forbids nested selection *sets* and object leaves, never a list of scalars/enums selected as a plain leaf. `restrictions` is diffed normally on `project`. |
| **P3-D13** | **`openshift`/`kubernetes` become diffable, not `diff_ignore`d** | `AddProjectInput.openshift` is `Int` while `Project.openshift` is `Openshift`. Under the depth-2 rule the deploy target was settable but unreadable, so `project` would have had to `diff_ignore` it and silently never detect a change. Under P3-D10 the module reads `openshift { id }` (a bounded object hop) and diffs the id. `diff_ignore` is reserved for fields with no readable state at all, not for rule artefacts. |
| **P3-D14** | **One list selection per document** | v1's `projectInfo` nested five object lists into one document; the object-beneath-list prohibition alone blocks its actual per-row expansion, but a cap is still needed so a future document cannot reassemble `projectInfo`'s breadth — five *scalar-leaf* lists in one read — even with every individual leaf legal under P3-D10. A composite info module wanting both `environments` and `envVariables` issues two reads, not one; each is separately cacheable and separately permissioned, the same reasoning P3-D2 already applied to `env_variable`'s own list read. |

# P3-S1 — `codegen/` scaffold + `codegen-v3` container

## Goal

A place for the generator to live that cannot leak `graphql-core` (or any of
its transitive dependencies) into the environment that runs the shipped
collection's own unit tests, per D3 and P3-D6.

## Context

`codegen/` is `build_ignore`'d already (P1-S1) and excluded from
`ansible-test`'s view via the existing `tests` "development artifact" framing
in `galaxy.yml`'s `build_ignore` comment. What's missing is a *test* story for
`codegen/` itself — nothing in Phase 1/2 exercises it, because nothing in
Phase 1/2 needed `graphql-core`.

## Files to create

```
codegen/__init__.py
codegen/requirements.txt
codegen/tests/__init__.py
codegen/tests/test_scaffold.py
.docker/Dockerfile.codegen-v3
```

## Files to modify

```
docker-compose.yml       # + codegen-v3 service
Makefile                 # + codegen-test / codegen-shell targets
```

## Design

`codegen/requirements.txt`:

```
graphql-core>=3.2,<4
Jinja2>=3.1,<4
PyYAML>=6,<7
pytest>=8,<9
```

`.docker/Dockerfile.codegen-v3` — a plain Python 3.11 image, `pip install -r
codegen/requirements.txt`, no `ansible-core`. Deliberately **not** based on
`ghcr.io/salsadigitalauorg/ansible-test` — the point of this container is
that it does *not* have `ansible-core`'s test machinery, proving `codegen/`
has no dependency on it either.

`docker-compose.yml` addition, modelled on the existing `graphql-mock-v3`
service block style:

```yaml
  codegen-v3:
    build:
      context: .
      dockerfile: .docker/Dockerfile.codegen-v3
    volumes:
      - .:/work
    working_dir: /work
    command: ["pytest", "codegen/tests", "-v"]
```

`Makefile` additions:

```makefile
codegen-test:            ## Run codegen's own test suite in its own container
	docker compose run --rm codegen-v3

codegen-shell:
	docker compose run --rm --entrypoint bash codegen-v3
```

`codegen/tests/test_scaffold.py` — deliberately minimal for this story; later
stories add real coverage as `codegen/` gains modules to test:

```python
def test_graphql_core_importable():
    """Confirms the container has the generator's actual dependency,
    not just a package that happens to share the name."""
    import graphql
    assert hasattr(graphql, 'build_schema')


def test_vendored_sdl_parses():
    """First real use of graphql-core against the SDL this collection
    ships -- proves the P2-S7 unresolved assumption (SDL loads under a
    graphql-import-based loader) generalises to graphql-core's own
    parser, which is what codegen/ actually uses at generation time.
    P2-S7 only proved the mock server's loader; this proves the
    generator's."""
    from pathlib import Path
    from graphql import build_schema
    sdl = Path(__file__).parents[2] / 'schema' / 'lagoon-2.33.0.graphql'
    schema = build_schema(sdl.read_text())

    assert schema.mutation_type is not None
```

### Implementation notes

- `codegen/__init__.py` stays empty (no `from __future__ import` header
  needed for an empty `__init__.py`, per `AGENTS.md`'s stated exemption).
- No `ansible_collections.*` import anywhere under `codegen/` — the generator
  reads the SDL and an allowlist file, and writes plain text. It has no
  reason to import anything from `plugins/`.
- Do **not** add `codegen-v3` to the `test-v3` service's `depends_on` or any
  shared network — the isolation is the point.

## Testing requirements

Both tests above must fail in `test-v3` (no `graphql-core` there — confirms
the isolation) and pass in `codegen-v3`.

## Acceptance criteria

- [ ] `docker compose run --rm codegen-v3` builds and passes both tests.
- [ ] `docker compose run --rm test-v3 units --requirements` remains green
      and unaffected — `codegen/` is invisible to it.
- [ ] `python -c "import graphql"` fails inside `test-v3` (confirms isolation
      is real, not accidental).
- [ ] `make codegen-test` and `make codegen-shell` both work.

## Verification commands


- Is `schema/lagoon-2.33.0.graphql` read from the same path `Makefile`'s

# P3-S2 — `module_utils/lookup.py`

## Goal

Name→id resolution for the two lookup shapes the real SDL actually has,
cached controller-side for the run, per parent plan §7.3.

## Context

`environment` is the resource that genuinely needs this (P3-D2):
`AddEnvironmentInput.project: Int!` needs a project name → id lookup before
create; `updateEnvironment(id: Int!, ...)` and `deleteEnvironment(name:
String!, project: String!, ...)` need different resolutions again. This
story builds the general mechanism `resource.py` (P3-S3) calls into, not
anything `environment`-specific — the allowlist declares which lookups a
module needs (parent plan §6, `lookups:` key), this module resolves them.

`errors.py` (P1-S3) already has `LagoonNotFoundError` and
`LagoonAmbiguousResultError` with the right shape (`resource`, `query`,
`arg`, `value`, optional `count`) — this story is the first caller of both.

## Files to create

```
plugins/module_utils/lookup.py
tests/unit/plugins/module_utils/test_lookup.py
```

## Design

```python
def resolve_lookup(client, lookup_config, value, cache=None):
    """Resolve one declared lookup to a concrete id.

    lookup_config is one entry from the allowlist's `lookups:` map, e.g.:
        {'query': 'projectByName', 'arg': 'name', 'returns': 'id'}

    client is a constructed LagoonClient. value is the alias-param value
    supplied by the caller (e.g. the project name).

    Cache key is (lookup_config['query'], lookup_config['arg'], value).
    cache is a plain dict the caller owns and passes in -- this function
    never constructs its own cache, so its lifetime is entirely the
    caller's decision (module-level for the in-memory case, matching
    P2-D1's token cache scoping).

    Raises LagoonNotFoundError if the query returns no result, or
    LagoonAmbiguousResultError if it returns more than one -- never
    falls through to a null id.
    """


def invalidate_lookup(cache, lookup_config, value):
    """Remove one cache entry. Called after any successful create/delete
    affecting that resource type, and unconditionally when state=absent
    (the resource may have just been deleted) -- per parent plan §7.3."""
```

### Implementation notes

- One flat query per lookup, built via `LagoonClient.build_query()` —
  `lookup.py` must not construct GraphQL documents any other way; reuse the
  existing depth-2 guardrail's coverage rather than inventing a second query
  path the sweep doesn't see.
- The query is expected to return a single nullable object (e.g.
  `projectByName(name: $name): Project`), not a list — that's why ambiguity
  detection here is different from `env_variable`'s list-read-and-filter
  path in P3-S11: a `List` result there is expected and filtered
  client-side; a non-list lookup query here returning more than one logical
  match (which can't actually happen syntactically, but a lookup config with
  `returns` pointing at a list field would silently misbehave) must be
  rejected by validating `lookup_config['returns']` resolves to a scalar
  before the first real call, not discovered at runtime.
- Cache invalidation is the caller's responsibility to *call*; this module
  only provides the mechanism (`invalidate_lookup`). `resource.py` (P3-S3)
  is the caller that decides when.

## Testing requirements

1. Cache hit: two calls with the same `(query, arg, value)` — the client's
   `execute()` is called exactly once (mock and assert call count).
2. Cache miss on a different `value` — two client calls.
3. `LagoonNotFoundError` raised (not returned as `None`) when the query
   result is null, with `resource`/`query`/`arg`/`value` populated correctly
   for message construction.
4. `invalidate_lookup` removes exactly the targeted entry, leaving unrelated
   cache entries (different query, different value) intact.
5. A lookup value containing GraphQL-significant characters (`{`, `"`,
   whitespace) passed as a **variable value**, never interpolated into the
   query text — assert the document passed to `client.execute()` is
   independent of `value`, only `variables` changes.

## Acceptance criteria

- [ ] Cache key is exactly `(query, arg, value)`, verified by a test that
      constructs two lookups differing only in one of the three components
      and confirms both hit the network.
- [ ] Never returns `None` on an empty/ambiguous result — always raises.
- [ ] No `ansible.errors` import (AST guard test, same pattern as every
      other `module_utils` file).
- [ ] User-supplied `value` never appears in the query document, only in
      `variables`.

## Verification commands

```sh
docker compose run --rm test-v3 units -v --requirements \
  tests/unit/plugins/module_utils/test_lookup.py
```

## Review focus

- Is the ambiguity/not-found distinction actually tested against different
  result shapes (`null` vs. a query misconfigured to point at a list), or
  only the happy path?
- Does the cache genuinely key on the value, not just the lookup name (a
  bug here would resolve every project to whichever one was looked up
  first)?

## Commit

```
feat(v3): add name-to-id lookup resolution with per-run caching

One flat query per declared lookup, cached by (query, arg, value) for
the caller-owned cache dict's lifetime. Raises LagoonNotFoundError or
LagoonAmbiguousResultError rather than ever returning a null id.

Refs docs/plans/v3-refactor.md 7.3
```

# P3-S3 — `module_utils/resource.py` — `LagoonResourceModule`

## Goal

The read/diff/mutate/check_mode engine every generated (and hand-written)
resource module subclasses. This is the story the parent plan's §7.4 calls
"where the real engineering effort sits" — `check_mode` and `--diff`
correctness are the acceptance bar, and v1 has nothing equivalent to port.

## Context

Moved into Phase 3 from the original Phase 4 split (P3-D4) because the Phase
3 gate cannot close without it — "generate `project`/`environment`/
`env_variable`... confirm `check_mode`/`--diff` are correct" is meaningless
without the engine that produces the diff. P3-S4 is this story's first real
caller, hand-written, before any generator code exists.

## Files to create

```
plugins/module_utils/resource.py
tests/unit/plugins/module_utils/test_resource.py
```

## Design

Directly implements parent plan §7.4's flow:

```python
class LagoonResourceModule:
    """Base class for read-diff-mutate resource modules.

    Subclasses declare (as class attributes or constructor args, per
    implementer's judgement -- pick one and be consistent across every
    generated module, since the templates in P3-S9 hard-code the shape):

      - read_query, read_arg: the flat query used to fetch current state
      - fields: scalar fields returned by the read query
      - diff_ignore: fields excluded from the diff (server-computed)
      - create_mutation, update_mutation, delete_mutation: mutation names
      - id_field: the field in the read result used as the mutation's
        `id` argument for update/delete
      - no_log_fields: field names whose diff reports changed/unchanged
        only, never either side's value (P3-D7)
      - enum_case_normalise: {field: 'upper'|'lower'} case-normalisation
        applied to the *read* side before diffing (P3-D9)
    """

    def run(self, module, client, lookups):
        """module: AnsibleModule. client: constructed LagoonClient.
        lookups: dict of already-resolved lookup values (ids), keyed by
        the allowlist's lookup name -- resource.py never calls lookup.py
        itself; the caller (module main()) does, so resource.py stays
        testable with plain dicts and no GraphQL client for the lookup
        step.
        """
        current = self._read(client, module.params)
        desired = self._desired_from_params(module.params)

        if module.params['state'] == 'present':
            if current is None:
                return self._create(module, client, desired)
            diff = self._diff(current, desired)
            if not diff:
                return self._unchanged(current)
            return self._update(module, client, current, desired, diff)
        else:
            if current is None:
                return self._unchanged(None)
            return self._delete(module, client, current)
```

### Implementation notes

- **`check_mode` short-circuits after diff computation, before any mutation
  call.** This is the one behaviour every test in this story must exercise
  at least once — a `check_mode=True` run must produce the identical
  `changed`/`diff` result as the equivalent real run, and must make zero
  calls to `client.execute()` for create/update/delete (read calls are
  fine and expected).
- **Diff shape:** `{'before': {...}, 'after': {...}}`, restricted to
  `fields` minus `diff_ignore`, matching Ansible's own `--diff` contract
  (`ansible.module_utils.common.text.converters` conventions — check
  existing Ansible core modules for the exact expected shape rather than
  inventing one).
- **`no_log_fields` (P3-D7):** for each such field, replace both `before`
  and `after` values in the diff dict with a sentinel indicating
  changed/unchanged (e.g. omit the field from `before`/`after` entirely and
  add a top-level `diff['changed_no_log_fields'] = ['value']` when it
  differs) — pick one shape and document it in this file's docstring, since
  P3-S11 depends on it exactly.
- **`enum_case_normalise` (P3-D9):** applied to the *read* result only,
  before the diff comparison — the desired-state value from `module.params`
  is already in the case the argspec's `choices` enforces (upper, matching
  the SDL enum), so only the read side needs normalising.
- State transitions, verbatim from §7.4:
  - `present`, absent remotely → create
  - `present`, present + no diff → `changed=False`, exit
  - `present`, present + diff → update
  - `absent`, present → delete
  - `absent`, absent → `changed=False`, exit
- Re-read after a real (non-check-mode) mutation and return the fresh state,
  not the pre-mutation `desired` dict — the server may normalise or default
  fields the caller didn't set explicitly.
- Where no read query exists for a resource (documented risk in parent plan
  §11), this class must support a `read_query=None` mode: every `present`
  call is unconditionally a create/update with `changed=True`, never a faked
  diff. Not exercised by the three gate resources (all three have a real
  read), but the interface must not preclude it — a resource without one
  shouldn't need a different base class.

## Testing requirements

Every state-transition branch from §7.4, each with and without
`check_mode`:

   mutation call, reports `changed=True`.
2. `present` + present + no diff → `changed=False`, no mutation call

3. `present` + present + diff → update; check-mode variant identical

4. `absent` + present → delete; check-mode variant, no mutation call.
5. `absent` + absent → `changed=False`, no mutation call.
6. `diff_ignore` fields excluded from the diff even when they differ between

7. `no_log_fields`: value present in `module.params` but absent from the

8. `enum_case_normalise`: read returns `'runtime'`, desired is `'RUNTIME'`

# P3-S5 — Port `argspec.py` to `codegen/`

## Goal

GraphQL input type → Ansible argspec, fixing the three defects found
verifying v1's implementation against the real SDL, before any allowlist or
template code depends on it.

## Context

Parent plan §2.1: "do not rewrite these from scratch — port them." This
story is the port. It is **not** a copy — three concrete defects in
`api/plugins/module_utils/argspec.py` would generate wrong or unsafe output
against `schema/lagoon-2.33.0.graphql`:

1. `generate_argspec_for_input_type`'s list-type branch hard-codes
   `dict(type='list', elements='dict')` unconditionally. Every scalar/enum
   list in the real SDL (`autogeneratedRoutePrefixes: [String]`,
   `restrictions: [Restriction]`, `problemSources: [String]`) would get a
   wrong `elements` and, for the enum case, silently lose its `choices`.
2. No `no_log` emission at all — a straight port would generate a `project`
   module that logs `privateKey` in plaintext argspec output, and an
   `env_variable` module that does the same for `value` (P3-D7 depends on
   this being fixed here first).
3. `generate_argspec_from_input_object_type`'s recursive descent has no
   depth limit or cycle guard — untested against the real SDL's actual
   nesting (e.g. `AutogeneratedPathRouteInput` inside `UpdateProjectPatchInput`
   inside `UpdateProjectInput`), which is shallow in practice but the v1 code
   doesn't verify that assumption anywhere.

## Files to create

```
codegen/argspec.py
codegen/tests/test_argspec.py
```

## Design

Signature-compatible with v1's functions (same names, same call shape) so
the port is auditable line-by-line against `api/plugins/module_utils/
argspec.py`, but operating on `graphql-core`'s types directly (no `gql`
DSL wrapper — v1 imports `gql.dsl.DSLField`; this port takes a
`graphql.GraphQLSchema` and resolves fields/args from it directly, since
`gql` is not a `codegen/` dependency per D3's "generator-only, and
specifically `graphql-core`, not `gql`" framing).

```python
def generate_argspec_from_mutation(schema, mutation_name, no_log_fields=()):
    """schema: graphql.GraphQLSchema. mutation_name: e.g. 'addProject'.
    no_log_fields: field names (post snake_case conversion) that must
    carry no_log=True -- sourced from the allowlist (P3-S8), not
    inferred from field names (no heuristic like "contains 'key'" --
    explicit declaration only, so coverage is auditable)."""

def generate_argspec_for_input_type(graphql_type, no_log_fields, path):
    """path: tuple of field names from the mutation root, used to key
    no_log_fields for nested inputs and to raise a clear error on
    unexpected recursion depth."""
```

### Implementation notes, each fixing one defect above

1. **List types:** inspect the wrapped type. `GraphQLScalarType` → `type:
   'list', elements: <scalar mapping>` (`String`→`str`, `Int`→`int`,
   `Boolean`→`bool`); `GraphQLEnumType` → `type: 'list', elements: 'str',
   choices: [...]`; `GraphQLInputObjectType` → `type: 'list', elements:
   'dict', options: {...}` (this is the only case where v1's hard-coded
   value was actually correct).
2. **`no_log`:** any field whose full dotted path (from `path`) matches an
   entry in `no_log_fields` gets `no_log=True` merged into its generated
   spec dict, after the type-driven generation, so it composes with any
   argspec shape.
3. **Depth guard:** raise a clear `ValueError` (this is generator-time code,
   not runtime `module_utils` — no `LagoonError` taxonomy applies here) if
   recursion exceeds a small fixed depth (4 is generous for this SDL; tune
   after checking the deepest real nesting). This must never fire silently
   as infinite recursion — it is a build-time signal that the allowlist
   is asking for something the generator doesn't support yet.

## Testing requirements

Run in `codegen-v3` (pytest, not `ansible-test`):

1. `AddProjectInput` end to end — argspec matches every field's real
   GraphQL type (spot-check `name` → `required: True, type: 'str'`,
   `autoIdle` → `type: 'int'`, `availability` → `type: 'str', choices:
   [...]` from `ProjectAvailability`).
2. `UpdateProjectPatchInput.restrictions: [Restriction]` → `type: 'list',
   elements: 'str', choices: [<Restriction's 5 values>]` — the exact case
   v1's port gets wrong.
3. `UpdateProjectPatchInput.autogeneratedPathRoutes:
   [AutogeneratedPathRouteInput]` → `type: 'list', elements: 'dict',
   options: {fromService: ..., toService: ..., path: ...}`.
4. `no_log_fields=('privateKey',)` against `AddProjectInput` → `privateKey`'s
   generated spec has `no_log=True`; every other field does not.
5. `no_log_fields=('value',)` against `EnvVariableByNameInput` → `value` has
   `no_log=True`.
6. Depth guard fires (raises, does not hang) on a synthetic schema
   constructed in the test with recursion exceeding the configured limit —
   do not rely on the real SDL happening to be shallow enough; prove the
   guard with a fixture built to violate it.
7. `GraphQLNonNull` wrapping is preserved through every branch above
   (`required: True` survives being wrapped around a list/enum/object type,
   not just a bare scalar).

## Acceptance criteria

- [ ] All seven cases pass.
- [ ] Every list-typed field on `AddProjectInput`/`UpdateProjectPatchInput`/

## Goal

The reusable version of P3-S4's hand-written update-path wrapping: given a
flat argspec-shaped dict and a mutation's real input shape, build the
correct wire payload — flat for `addProject`, `{id, patch: {...}}` for
`updateProject` — and enforce create-only/update-only fields (P3-D1).

## Context

## Files to create

```
codegen/wire.py
codegen/tests/test_wire.py
```

## Design

```python
def build_wire_payload(mutation_shape, params, state):
    """mutation_shape: derived from the allowlist + SDL at generation
    time (P3-S8/P3-S9 own producing this; this function only consumes
    it) -- describes whether the target mutation is flat or
    {id, patch}, and which fields are create-only/update-only.

    params: the flat dict of resolved module params (snake_case,
    already converted to the values the wire format wants).

    state: 'create' | 'update' -- which mutation is being targeted,
    since create-only/update-only enforcement differs by direction.

    Raises LagoonConfigError-shaped info (this is generator-time code;
    return a structured error description, do not import
    module_utils.errors here -- codegen/ has no runtime dependency on

    an update-only field is present for state='create'.
    """
```

Also emits, per module, the small runtime snippet the generated module's
`run_module` embeds to perform this same operation at runtime — since
`wire.py` itself is a `codegen/`-only (dev-time) tool, but the *behaviour*
it encodes must exist in the shipped module. Decide and document one of:
(a) the generator emits the wire-shaping logic as literal generated Python
in each module (consistent with "modules hold 100% of the business logic",
no runtime dependency on `codegen/`), or (b) a small `wire`-equivalent
helper lands in `module_utils/` for generated modules to import. **(a) is
preferred** — it keeps the zero-runtime-dependency property trivially true
and matches P3-S4's precedent (hand-written, not calling into a shared
helper).

2. Nested mutation (`updateProject`): returns `{id: <id>, patch: {<params

3. Create-only field present with `state='update'` → raises/returns an

4. Update-only field present with `state='create'` → same, for the create

5. A field that is valid on *both* directions (the common case — most
   fields) is never flagged by 3/4's checks.
6. Round-trip against `project`'s real shape from P3-S4: build the payload
   the generator would produce and diff it against what P3-S4's hand-
   written module actually sends for the same input (this is the first
   place the "generator output == golden target" property gets checked at
   the wire-payload level, ahead of P3-S9's whole-file check).

## Acceptance criteria

- [ ] All six cases pass.
- [ ] Test 6's diff is exact — not "similar shape", byte-for-byte on the
      dict structure (dict equality, key order doesn't matter for a dict

- [ ] The (a) vs (b) decision above is made and stated in the module
