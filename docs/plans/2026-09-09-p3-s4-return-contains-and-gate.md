# RETURN `contains:` for `project`, and P3-D5's gate softened to structural equivalence

**Date:** 2026-09-09
**Branch:** `3.x`
**Status:** Ready for implementation
**Audience:** the `code` agent implementing this change

## Why these two are one change

`plugins/modules/project.py`'s `RETURN` block documents the returned
`project` dict as a whole (a `sample:`) with no `contains:` block --
unlike `plugins/modules/whoami_info.py`, which documents every one of its
seven returned fields under `contains:`. That is a real documentation gap:
nothing currently tells a user what fields `project` returns, their types,
or that two of the module's 42 tracked wire fields are never present in
the returned dict at all.

Adding a 40-entry `contains:` block is cheap under a *structural*
equivalence gate and expensive under P3-D5's current byte-for-byte one --
hand-writing it today means also anticipating the generator's exact
future indentation and key order, or re-writing it again once the
generator exists. So the two changes are done together: soften the gate
first (Part 3), then add the block knowing it will be compared on meaning,
not on text.

## Part 1 -- `plugins/modules/project.py`: add `contains:` to `RETURN`

**40 entries**, covering all of `_FIELDS` except `privateKey` and
`addOrgOwner` (never present in the returned dict -- see below).

### Description sourcing -- same 29/13 (minus the 2 omitted = 28/12) split as the options block

Measured against the real vendored SDL:

| Source | Count |
| --- | --- |
| `Project` SDL description, reused verbatim | 28 |
| Hand-written (no SDL description anywhere) | 12 |

The 12 with no SDL description: the five `activeSystems*` fields,
`sharedBaasBucket`, `restrictions`, and the five ARC-backed names
(`autogeneratedRoutes`, `autogeneratedRoutesPullrequests`,
`autogeneratedRoutePrefixes`, `autogeneratedPathRoutes`,
`disableRequestVerification` -- confirmed undescribed on
`AutogeneratedRouteConfig` too, not just on `Project`).

**All 12 already have wording in `DOCUMENTATION`'s `options:` block --
reuse it**, dropping any input-path caveat that makes no sense for a
returned value (e.g. "Applied only when updating an existing project").

### Types must reflect the post-flattening shape, not the raw SDL type

`_flatten_hops()` rewrites three object-typed hops back into scalar/list
wire fields before the caller ever sees them. `RETURN` must describe what
the caller actually receives:

| Field | Raw SDL type | Returned type (post-flattening) |
| --- | --- | --- |
| `openshift` | `Openshift` (object) | `int` -- flattened to `Openshift.id` |
| `kubernetes` | `Kubernetes` (object) | `int` -- flattened to `Kubernetes.id` |
| `autogeneratedRoutes` | n/a (ARC leaf `enabled: Boolean`) | `bool` |
| `autogeneratedRoutesPullrequests` | n/a (ARC leaf `allowPullRequests: Boolean`) | `bool` |
| `disableRequestVerification` | n/a (ARC leaf, same name) | `bool` |
| `autogeneratedRoutePrefixes` | n/a (ARC leaf `prefixes: [String]`) | `list` / `str` |
| `autogeneratedPathRoutes` | n/a (ARC leaf `pathRoutes: [AutogeneratedPathRoute]`) | `list` / `dict`, with its own nested `contains:` for `from_service`/`to_service`/`path` |
| `restrictions` | `[Restriction]` (enum list) | `list` / `str` |

Every other field is a plain scalar read straight off `Project` -- map
`Int`/`String`/`Boolean`/`Float`/`ID` to `int`/`str`/`bool`/`float`/`str`
directly, and any other enum (`availability`: `ProjectAvailability`) to
`str`.

### Two fields omitted from `contains:` entirely

- **`privateKey`** -- in `_FIELDS` and `_NO_LOG_FIELDS`, deliberately
  excluded from `_READ_SELECTION` (P3-D17). Genuinely never present in
  the returned dict on any path. The existing `RETURN` prose already
  states this ("C(privateKey) is never included..."); keep it, do not
  add a `contains:` entry for a key that never exists.
- **`addOrgOwner`** -- not a field on `Project` at all; has no SDL
  presence to describe. Add one prose line to the dict-level description
  stating it is accepted on create but never returned, alongside the
  existing `privateKey` line.

This is a deliberate divergence from P3-S7's current `render_return`
design (see Part 2) and must be recorded there, not left implicit --
otherwise a future generator run re-adds a `contains:` entry describing a
key that can never appear.

## Part 2 -- amend P3-S7 (`docs/plans/v3-phase3-stories.md`)

`render_return(module_name, fields, no_log_fields)` (as currently
specified) takes `fields` and would emit a `contains:` entry for every
member, including `privateKey` -- a no_log field the design assumes
should be documented as "present but withheld", when for `project` it is
never present in the read at all.

Changes needed:

- `render_return` must additionally take the module's read selection and
  hop-flattening map. Rule: **omit any field absent from the read
  selection** from `contains:`; note its absence in the dict-level
  description instead of describing it as a withheld no_log value.
- Add a test case: RETURN and `DOCUMENTATION`'s `options:` resolve
  descriptions from the *same* `descriptions:` override table (P3-D3) --
  one table, two consumers, not two independently-maintained prose sets.
- Record that the 12 hand-written strings landing in `project.py` in this
  change are the seed for that table once P3-S8 creates
  `codegen/allowlist.yml` (which does not exist yet -- hence inline here,
  not pre-created early). They will exist in two places (RETURN and
  options) until P3-S8 lands; that duplication is temporary and
  intentional, not drift.

## Part 3 -- soften P3-D5's gate from byte-for-byte to structural equivalence

### The problem with byte-for-byte, concretely

P3-D5 (`v3-phase3-stories.md`) and P3-S9's acceptance criteria currently
require the generated `project.py` to be textually identical to the
hand-written one, down to the marker-header amendment needed to make that
literal. Every incidental detail of the hand-written file -- comment
wording, blank-line placement, key order in a literal dict -- becomes a
constraint the generator must reproduce exactly, discovered one gap at a
time as each is found (this RETURN gap is the second, after the `id`
create-only misclassification in
`docs/plans/2026-09-08-p3-s4-id-misclassification.md`).

### The replacement definition

Not "close enough" or "same fields, different formatting" -- compare
**parsed structures**, so the check remains as strict as byte-for-byte on
everything that is actually load-bearing, and only tolerant of formatting
that never was:

| Artefact | Comparison |
| --- | --- |
| `argument_spec()` | `assertEqual` on the returned dict -- exact, independent of source formatting |
| `DOCUMENTATION` / `EXAMPLES` / `RETURN` | parse as YAML, compare as data structures |
| Module-level constants (`_FIELDS`, `_READ_SELECTION`, `_HOP_FLATTENING`, `_CREATE_ONLY`, `_UPDATE_ONLY`, `_DIFF_IGNORE`, `_NO_LOG_FIELDS`, `_CREATE_REQUIRED`, `_UNREADABLE_CREATE_ONLY`) | evaluate as literals (reuse `query_depth.py`'s `_literal_from_ast` machinery), compare values |
| GraphQL documents actually built | compare the built document strings -- `query_depth.py`'s sweep already reconstructs these via `build_query`, reuse that rather than re-deriving |
| **Behaviour** | run P3-S4's full `test_project.py` suite against the generated module in place of the hand-written one |

Several of these are *stronger* than a text diff: dict equality on the
argspec catches a wrong `type=` regardless of surrounding layout, and the
unit-suite run is genuine behavioural proof a text diff never actually
gave (P3-S9's existing acceptance criteria already required this
separately -- promote it to primary evidence, not a supplementary check).

### What is genuinely lost -- stated plainly, not glossed over

Byte-for-byte also pinned **comments and docstrings**. Under structural
equivalence, a generated module whose prose diverges from the
hand-written original's now passes. This matters here because
`AGENTS.md` is strict about comment style (standalone, terse, no story/
plan references). Mitigation: comments originate from templates, so
review them **once**, explicitly, at P3-S9 as a named review-focus item
(added below) -- rather than relying on a continuous diff that was never
really checking prose quality in the first place, only textual identity.

### Consequence: the marker-header amendment is no longer needed

P3-S9's current design (`v3-phase3-stories.md`) requires retroactively
amending P3-S4's committed file to add a "GENERATED FILE -- DO NOT EDIT"
marker header, purely so the byte-for-byte diff has nothing left to
explain away. Under structural equivalence the header is not a compared
artefact at all, so amending P3-S4's file to add one is no longer
necessary. Drop that requirement from P3-S9's design and commit message
template.

## Part 4 -- amend P3-S9 (`v3-phase3-stories.md`)

- Retitle the story from "gate: reproduce `project` byte-for-byte" to
  "gate: reproduce `project`'s structure and behaviour".
- Rewrite testing-requirements 1-2 (currently: diff the rendered file
  against the committed one, expect zero lines) as the structural
  comparisons in the table above.
- Keep testing-requirements 3-6 unchanged (`--check` mode against the
  real tree, marker-header presence on generated files generally,
  `docgen.py`'s build-failure behaviour) -- these are unaffected by this
  change.
- Replace the "do not relax to close enough" acceptance criterion with
  the structural definition above. Keep, and promote to primary evidence,
  the existing criterion that the full unit suite passes against the
  generated module in place of the hand-written one.
- Keep the existing review-focus question about whether the template was
  built backwards from the golden file or independently designed and
  patched until a diff happened to close -- it remains the right question,
  and matters more now that cosmetic divergence is tolerated.
- Add a new review-focus question: were the generated module's comments
  and docstrings actually read and judged against `AGENTS.md`'s comment
  conventions, given they are no longer diffed automatically?
- Remove the marker-header retroactive-amendment step from the design and
  from the story's commit-message template.

## Verification

```sh
docker compose run --rm lint-docs-v3
docker compose run --rm test-v3 units -v --requirements
```

`lint-docs-v3` is the primary gate here: `antsibull-docs` validates
`contains:` structure, required keys (`description`, `type`, `returned`)
and type correctness, and separately rejects a `no_log:` key appearing in
any documentation block (not relevant to this change, but the same lint
pass that would catch it if introduced by mistake).
